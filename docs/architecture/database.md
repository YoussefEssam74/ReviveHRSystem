# Database Architecture — PostgreSQL

## Why PostgreSQL

| Factor | PostgreSQL | SQL Server | MySQL |
|--------|-----------|------------|-------|
| **License** | Free, open-source (MIT) | Paid for production (Express has limits) | Free (GPL) |
| **EF Core Support** | Excellent (Npgsql) | Native, best | Good (Pomelo) |
| **On-Premises** | Zero licensing cost | Expensive | Zero cost |
| **JSONB Columns** | ✅ Native, indexed | JSON (limited) | JSON (limited) |
| **Full-Text Search** | ✅ Built-in | ✅ Built-in | ✅ Built-in |
| **Row-Level Security** | ✅ Native | ✅ Native | ❌ No |
| **Audit/Temporal Tables** | ✅ Via triggers/extensions | ✅ Native temporal | ❌ Manual |
| **Scale (500-2000+ employees)** | Excellent | Excellent | Good |
| **Arabic/UTF-8** | ✅ Full Unicode | ✅ Full Unicode | ✅ Full Unicode |
| **Docker** | ✅ Official image | ❌ Linux container only | ✅ Official image |
| **Community** | Massive | Massive (.NET focus) | Massive |

**Decision: PostgreSQL** — zero licensing cost for on-premises, excellent EF Core support via Npgsql, native JSONB for flexible audit logs, and scales comfortably for 20-50+ gyms with 500-2000+ employees.

## Database Conventions

### Naming
- Tables: `PascalCase` (EF Core default) — `Employees`, `Gyms`, `ShiftCycles`
- Columns: `PascalCase` — `FirstName`, `GymId`, `CreatedAt`
- Foreign Keys: `FK_{ChildTable}_{ParentTable}_{Column}`
- Indexes: `IX_{Table}_{Column(s)}`
- Unique Constraints: `UQ_{Table}_{Column(s)}`

### Common Columns
Every entity should include:
```
Id          : Guid (primary key, generated by application)
CreatedAt   : timestamptz (set on insert, never modified)
UpdatedAt   : timestamptz (set on every update)
CreatedBy   : Guid? (UserId who created)
UpdatedBy   : Guid? (UserId who last modified)
IsDeleted   : bool (soft delete flag, default false)
```

### Soft Delete
- Business records (employees, candidates, gyms, attendance) use soft delete
- Queries must always filter `WHERE IsDeleted = false` unless explicitly requesting archived data
- EF Core global query filters enforce this

### Audit Log Table
```sql
CREATE TABLE "AuditLogs" (
    "Id"          uuid PRIMARY KEY,
    "UserId"      uuid NOT NULL,
    "Action"      varchar(50) NOT NULL,     -- Created, Updated, Deleted, etc.
    "EntityType"  varchar(100) NOT NULL,    -- Employee, AttendanceRecord, etc.
    "EntityId"    uuid NOT NULL,
    "OldValues"   jsonb,                    -- JSONB snapshot of previous state
    "NewValues"   jsonb,                    -- JSONB snapshot of new state
    "Timestamp"   timestamptz NOT NULL,
    "IpAddress"   varchar(45)
);
```

JSONB columns are ideal for audit logs because the schema of audited entities varies, and PostgreSQL can index JSONB fields efficiently.

### Notifications & Announcements

Two separate concerns:
- **Notifications** — system-generated, per-user, inbound (e.g. "Your request was approved")
- **Announcements** — HR-authored, broadcast, outbound (e.g. "Gym closed on Friday")

```
Notifications  ← system-triggered, per user
├── Id (PK)
├── UserId (FK → Users)
├── Title
├── Message
├── Type (enum: RecruitmentFollowUp, RequestUpdate, AttendanceIssue,
│               ScheduleUpdate, ContractExpiry, SystemUpdate, Announcement)
├── IsRead
├── LinkTo (URL path to relevant page)
├── CreatedAt
└── Common columns

Announcements  ← HR-authored broadcasts
├── Id (PK)
├── AuthorId (FK → Users)  ← the HR/Manager who composed it
├── Title
├── Body (text)
├── ScheduledAt (timestamptz, nullable — null = send immediately)
├── SentAt (timestamptz, nullable — set when actually delivered)
├── Status (enum: Draft, Scheduled, Sent, Cancelled)
└── Common columns

AnnouncementTargets  ← audience definition (many rows per announcement)
├── Id (PK)
├── AnnouncementId (FK → Announcements)
├── TargetType (enum: AllGym, Department, Role, Individual)
├── GymId (FK → Gyms, nullable — required when TargetType = AllGym or Department)
├── DepartmentId (FK → Departments, nullable — required when TargetType = Department)
├── RoleId (FK → Roles, nullable — required when TargetType = Role)
└── UserId (FK → Users, nullable — required when TargetType = Individual)

Delivery: When an announcement is sent, one Notification row is created per
matched recipient (Type = Announcement, LinkTo = announcement detail page).
This keeps the recipient's notification inbox as the single surface they check.
```

## Performance Considerations

### Indexes (Critical)
- `IX_Employees_GymId` — every employee query filters by gym
- `IX_AttendanceRecords_EmployeeId_Date` — unique, daily lookups
- `IX_ShiftAssignments_ShiftCycleId` — grid rendering
- `IX_Applications_VacancyId` — pipeline queries
- `IX_UserGymAccess_UserId` — authorization checks (every request)
- `IX_Notifications_UserId_IsRead` — notification bell count
- `IX_LeaveBalances_EmployeeId_LeaveType_Year` — unique, balance lookup per type per year
- `IX_Announcements_Status_ScheduledAt` — scheduled announcement dispatcher query
- `IX_AnnouncementTargets_AnnouncementId` — fan-out on send

### Connection Pooling
- Use Npgsql connection pooling (built into the provider)
- Minimum pool size: 5 (adjust based on concurrent users)
- Maximum pool size: 100

### Query Optimization
- Use `AsNoTracking()` for read-only queries
- Use projection (`.Select()`) for list views — don't load full entities
- Use split queries for entities with multiple collections
- Paginate all list endpoints (never return unbounded results)
